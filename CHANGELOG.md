# Changelog

## 0.2.0 (not released)

Renames

- The word `lane` is now `worker`. The word `pack` is now `recipe`. One named way to run a recipe is a setup, and its config key is `recipe.variant`. The word `brief` is now `assignment`. The tmux pane option is `@worker`.
- The state folder `.factory/briefs/` is now `.factory/orders/`. The file `.factory/protocol.md` is now `.factory/roles/worker.md`, and its managed block is `worker`.
- The config key `lanes` is now `workers`. The key `node.role` is now `node.layer`. The key `pack` of a project is now `recipe.variant`.
- Text that a user reads uses the plain words of `docs/glossary.md`: factory folder, factory list, work copy, assignment, worker window and terminal window. `factory help words` prints the words of the program.

File formats

- `factory.yaml` has schema 2. The new file `factory.local.yaml` has schema 1. See "Config files" below.
- The projects are in `recipe.projects`, and `recipe.id` names the recipe. A project has a `path`, which is one folder name in the factory folder, and an optional `url`, which is the clone URL. New keys: `tracker`, `approval`, `sources`, `parent` and `children`.
- The first `.factory/board.json` of a new factory has the queue key of the recipe (`merge` for the software recipe), an empty list of items and an empty list of tracks. `upgrade` renames the old queue key `queue` to the key of the recipe and changes nothing else in the file. See "The local board" below.
- The factory list `homes.json` holds the node id, the folder, the project paths and the origin of each factory. The origin is `own` or `received`.

Config files

- The factory folder holds two config files. `factory.yaml` is shared: git tracks it, and it goes to every machine. `factory.local.yaml` is private: git ignores it, and it has mode 600.
- The shared file holds the node, the board, the session settings, the limits and the recipe with its projects. The private file holds the owner, the proxies, the settings of a worker, the mode of each approval point, the links to other nodes and the local source of a project.
- New shared key `session.agent`. Its only value is `claude`, and `claude` is the default. A `factory.yaml` with no `agent` key loads with no upgrade.
- New shared key `limits.idle_after`, `<n>m` or `<n>h` from 1m to 24h, default `2h`. A `factory.yaml` with no such key loads with no upgrade.
- The shared file refuses a key of the private file. The error names the key and the private file. A proxy entry in `factory.yaml` fails the load.
- `init` writes the private file with mode 600. `start`, `init`, `node` and `upgrade` set a mode with group or other read bits back to 600 and print a notice. They stop with exit code 4 when the file has a group or other write bit, has another owner, or is a link. `doctor` and a dry run only warn about read bits.
- With `factory.yaml` and no `factory.local.yaml`, `start`, `doctor` and `node` exit with code 2 and name `init`.
- The only board is `local`. The other kinds parse, and `doctor` warns that their connector comes later.
- A node link (`parent` and `children`) accepts only a `file://` address on this machine. An `ssh://`, `https://` or relative address is refused.
- `factory` refuses a config file, a state file or a factory list file of more than 1,048,576 bytes. It does not read the rest of such a file. This holds for the config of a child that `doctor` and `node children` read.

The factory folder

- The factory folder is a git repo of its own, the config repo. It tracks `factory.yaml`, `.gitignore` and `setup/`. `init` makes the first commit.
- The `.gitignore` holds the share list between two marker lines. It ignores every other path. `upgrade` writes the part again and keeps the lines that you add.
- The coordinator runs in `coordinator/`, and `coordinator/CLAUDE.md` holds its role. The top of the factory folder holds no instruction file, so a worker never reads the text of the coordinator.
- `init` clones each project into a folder of the factory folder. The path of a project is one folder name. The names `coordinator`, `work-copies`, `setup`, `factory.yaml`, `factory.local.yaml`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `GEMINI.md` are reserved, in any letter case. `work-copies/` is the folder for the work copies of workers. `init` does not make it.
- Two text files hold your own text: `setup/coordinator.md` and `setup/roles/worker.md`. `init` and `upgrade` render them into `coordinator/CLAUDE.md` and `.factory/roles/worker.md`. The repo tracks the two setup files and does not track the two rendered files.
- If a stopped `init` left a temp folder `.factory.tmp-<pid>` in the factory folder, the next `init` and `doctor` name the folder and say that you can remove it by hand. They remove nothing.

`init`

- `factory init` proposes a folder. In a git work tree, it proposes a new factory folder beside the repo: `../<repo>-factory`. In a folder that holds git repos, it proposes a folder inside it: `./<folder>-factory`. It asks in a terminal window. `--yes` uses the proposal. With no terminal window and no `--yes`, it prints the proposal and exits with code 2.
- `init` clones the repo, or each repo, into the factory folder as a project. The old folder stays as it was, and `init` warns that it keeps the work that is not pushed. A folder that is a linked work tree of a listed repo is skipped, and `init` names it.
- `init` stops with exit code 1 for a factory folder inside a folder that the factory list holds. A factory folder can sit beside another one.
- New flags of `init`: `--yes`, `--layer N`, `--recipe ID`, `--project PATH|URL`, `--name ID`, `--owner-name NAME`, `--owner-github LOGIN` and `--approval POINT=MODE`.
- `--approval POINT=MODE` sets the mode of one approval point of the recipe. The mode is `owner` or `delegated`, and the default is `owner`. In a terminal window, `init` asks for each point that no flag names. `--yes` writes `owner` and refuses a flag that asks for `delegated` (exit code 2). A `delegated` choice with no terminal window, or inside a factory session, exits with code 4 and writes nothing.
- `--project` takes a path of a git work tree or a clone URL. A URL makes `init` clone the repo into the factory folder, in a folder with the name of the repo. A URL with a leading `-` is refused.
- `init` makes every check that needs no cloned project before it clones. If a later step fails, `init` removes the clones that it made and the empty folders that it made above them. It never removes a folder that was there before.
- `init` writes the factory folder into the factory list as its last step. If that fails, `init` exits with code 1, removes only what the run made, and prints no success line. A second `init` then works.
- A clone that takes longer than 300 seconds stops with a message that names the limit and suggests an ssh agent or `gh auth login`.
- `init` writes the `url` of each project from the origin of its repo, without credentials, and warns when the origin held some. A repo with no origin, or with a `file` URL, gets no `url`. Its local folder goes to `sources` in `factory.local.yaml`, and `init` and `doctor` warn that the factory cannot be shared with that repo.
- The commits of `init` and `upgrade` in the state repo and in the config repo run no git hook.
- A second `init` in a registered factory folder asks for each approval point again. This is how you change a mode later. It renders `coordinator/CLAUDE.md` again when a mode changes.
- If `init` cannot write the record of an approval point, it still succeeds. It prints a warning that names the point and the remedy, and the point counts as `owner`.

The factory list and the registration

- `init` writes the factory folder into the factory list: `$XDG_STATE_HOME/factory/homes.json`, or `~/.local/state/factory/homes.json`. The list is never under `~/.claude`. The check resolves links, and on macOS it ignores the case of letters.
- A command with `FACTORY_HOME` and no `--home` stops with exit code 1 when the current folder is inside another factory folder of the factory list. A `factory.yaml` in a project clone does not count. The message names both folders and the `--home` remedy. A hook always uses `FACTORY_HOME`.
- `doctor` warns with the new check `node-id` when another factory in the factory list has the same node id, because the sessions of both nodes then get the same names.
- The list file has mode 600, and its folder has mode 700. `factory` refuses a list file or list folder that another user owns or that a group or other user can write. The error names the path.
- Two `init` runs at the same time both keep their entry. A lock file `homes.json.lock` beside the list lets one run write at a time. A run tries 20 times, 50 ms apart, then stops with an error. A lock older than 5 seconds is taken over.
- When the list holds 200 factories, `init` first drops the entries whose folder has no config file. It keeps an entry whose folder it cannot check.
- A `factory.yaml` counts only at a factory folder that `init` registered: the list has an entry for the folder, the id of the entry is the `node.id` of the config, and the factory marker `.factory/node.json` is valid. If not, `start`, `doctor`, `node` and `upgrade` exit with code 4. They name the file, the reason and one remedy. The check holds for the walk up from the current folder, for `--home` and for `FACTORY_HOME`.
- A command finds the factory folder from the factory folder, from `coordinator/` or from a project clone. The order is `--home`, then `FACTORY_HOME`, then the nearest `factory.yaml` above the current folder, then the factory list.
- A command that finds no factory folder exits with code 2 and prints a hint. Version 0.1.0 exited with code 1.
- The `index` check of `doctor` warns when the factory list does not list the current factory folder.
- A received factory is a factory folder that you cloned from the config repo of another person or machine. `init` in it clones the projects, registers the folder and asks for your personal values, the mode of each approval point and the acceptance of the setup text. Then `start` works. A moved factory is a factory folder that is at another path now. `init` registers it again. A move ends each delegation, so each point counts as `owner`.
- The setup text needs your acceptance. `init` accepts the text that it wrote itself on a new factory. On a received factory, the acceptance covers every other file that the config repo tracks, too. After a change, `start` and `upgrade` show the change and ask in a terminal window outside a factory session. Otherwise they exit with code 4 and name the command.
- To share a factory, add a remote to the factory folder and push: `git remote add origin <url>`, then `git push -u origin main`. The work state in `.factory/` stays on its machine until FAC-M3.

`start`

- New command `factory start`. It starts a tmux session with the id of the node, with the windows `view` and `workers`. The coordinator runs in `coordinator/` in auto permission mode, with one `--add-dir` for `.factory/` and one for each project. There is no `--add-dir` for the top of the factory folder.
- The coordinator does not inherit `ANTHROPIC_BASE_URL`. The shells of the slot and of the worker window get none either. The coordinator gets the `PATH` of the shell that ran `start`. `start` sets `FACTORY_SESSION` to the node id in the environment of the session.
- The coordinator does not inherit any variable whose name starts with `CLAUDE`, except `CLAUDE_CONFIG_DIR` and the provider switches `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY` and `CLAUDE_CODE_USE_MANTLE`. So a `start` that runs inside a Claude Code session does not start the coordinator as a child of that session, and a name that a later Claude Code adds does not pass either. The program of the coordinator is the config key `session.agent`.
- The pane of the coordinator stays when its program ends at once. If a start step fails after the session is gone, `start` says so and tells you to run `claude` in the shell to read its error.
- A second `start` starts no second coordinator. If the program of the coordinator has ended, `start` warns, names the commands that remove the session and start it again, and adds `coordinatorEnded` to the JSON output.
- `--dry-run` prints the tmux calls and starts nothing. `start` works with a semicolon at the end of the factory folder, of a project folder or of the PATH.
- `start` checks the `safety` block of `coordinator/CLAUDE.md` first. It renders the block again when the block is intact and the current text differs. It exits with code 4 when the block is edited or missing, or when `coordinator/` or `coordinator/CLAUDE.md` is a link, also in a dry run.
- `start` exits with code 4 and starts no session when a check of the factory folder fails. The checks are in "Security" below.
- After the tmux server was killed, `start` resumes the recorded workers, too. The coordinator resumes with the session id of its pointer `.factory/state/coordinator-last-session` when the last-seen line of that session belongs to the coordinator, else it starts a new conversation. Each worker resumes with the session id of its last-seen line, under the rules of `worker resume`. A worker with no usable id, or with a wrong settings file in its work copy, is skipped with a warning that names it. A worker that does not start again is reported, the next worker still resumes, the session stays and the exit code is 0. One run asks each proxy once.
- When the session runs already, `start` resumes no worker. It warns once and names each recorded worker that has no live pane, with the command that starts it (`factory worker resume ID`). It writes the mark of the active machine when the mark does not name this machine.
- `start` writes the mark of the active machine, `.factory/active-machine.json`, with the id of this machine, and commits it. If the mark names another machine, `start` warns before it resumes any worker, names `factory shutdown` and exits with code 0. `shutdown` clears the mark of this machine and keeps a mark of another machine.
- `start` against a tmux session of the same name that belongs to another folder exits with code 4, and the remedy names `factory shutdown` in the folder that owns the session.

The last-seen hook and the settings write

- New command `factory hook EVENT`, for Claude Code and not for people. For `SessionStart`, `UserPromptSubmit`, `Stop` and `PreCompact`, it writes one last-seen line (session id, event, time and context percent) to `.factory/state/heartbeat/<session>`. It exits with code 0 on every path. It prints to stdout only for the `SessionStart` of a worker session (see below). It reads its input for at most 2 seconds, writes nothing for an input that is not valid or not whole by then, and never opens the transcript path.
- New command `factory hook statusline`, the status line wrapper that `start` and `init` write to the settings. It records the context percent (`context_window.used_percentage`, else the input tokens of `context_window.current_usage` divided by `context_window.context_window_size`) in the last-seen line, then prints the output of the command in `session.statusline` of `factory.local.yaml` as it is. The command gets the same input and 2 seconds. At the limit, every process that the command started stops. A SIGTERM, SIGHUP or SIGINT of the wrapper stops them too, and the wrapper exits with code 0. A SIGKILL of the wrapper can not be caught and leaves them running. With no command, or with a command that fails or takes too long, it prints `context N%`, and `context ?%` when the input gives no percent or is not whole after 2 seconds. It always exits with code 0, prints at most one line on stderr, writes only for a session that passes the checks of the hook, and never opens the transcript path.
- The hook and the status line wrapper write the last-seen line under a lock file in the same folder, `<session>.lock`. A writer reads the line again inside the lock, so a write never puts back older data. It waits 300 ms at most for the lock, and then it writes nothing: that update is skipped, and the next event or refresh sets it again. A lock file older than 2 seconds is taken over. A lock file that is a link stops the write, and the hook still exits with code 0 and prints one line on stderr.
- The hook and the status line wrapper accept two values of `FACTORY_SESSION`: the id of the node, and the id of a worker that has a valid record in `.factory/workers/<id>/worker.json`. A missing, invalid or linked record, and an id that is not a slug, give no write: the hook still exits with code 0 and prints one line on stderr. The id of the node never reads the registry.
- `factory hook SessionStart` gives a worker session its role text. For the `SessionStart` of a worker session it prints one JSON object, with the fields `hookEventName` and `additionalContext`. A start, a resume, a clear and a compact of a worker each raise that event. The coordinator session and the other five events print nothing to stdout. The text starts with a fixed source line and holds the worker rules of the package and the text of `setup/roles/worker.md` that the owner accepted. The hook never reads the rendered `.factory/roles/worker.md`, which is a copy for people. An edit of `setup/roles/worker.md` must be accepted again before the next clear or compact.
- The hook checks a link in the path of the setup file, the owner and the mode of the file and its folders, the size (at most 9000 characters, never cut), the encoding, a control character, a marker line of a managed block, the acceptance of the text, a read fault and the config. When a check fails, or the worker branch throws, it prints a fixed refusal text instead of the role text, and one fixed reason on stderr. A worker session also gets the refusal text when the input of the hook cannot be used, and the hook then records no session. It still exits with code 0. A reason of the role text holds no text of a file, no path and no text of an error. When the write of the last-seen line fails, the hook prints one more line on stderr with the reason of that failure, and that line can name a path. Each accepted setup file protects only its own text, so a change to `setup/coordinator.md` does not stop the delivery to workers.
- A worker with no hook of factory in its work copy fails closed, because it would get no role text. The answer no to the question about the hook settings of `worker new` leaves a work copy with no hook, and the launch refuses to start the worker (exit code 3). `worker resume`, `restart` and `reboot` refuse the same way. The refusal names the remedy: for a work copy that never had the hook, run `factory dismiss ID`, then `factory worker new ID --project PROJECT`, and answer yes. For a work copy with some of the hooks, run `factory upgrade`, then the command that stopped. A fault of the role text stops the same commands, and `worker reset` too, before any pane starts, any worker stops or any key is typed (`worker reset` gives exit code 4 for a link, a wrong owner or mode, or a setup file that is not accepted, else exit code 1. `worker new`, `worker resume`, `restart` and `reboot` check the factory folder first: in your own factory folder they give exit code 4 for a setup text that is not plain text, that holds a block marker, or that is larger than 65536 bytes, and they then give the same codes as `worker reset`, so a text above the cap of 9000 characters is exit code 1). `worker new` checks the role text before it makes the work copy, so a fault leaves no work copy, no branch and no record. The settings of a work copy that turn off all hooks, or that set `XDG_STATE_HOME` or `HOME` in `env`, stop the launch with exit code 4.
- A worker that already runs when you update gets the role text at its next clear or compact. The text enters a session only at its start, its resume, its clear and its compact.
- `factory hook EVENT` and `factory hook statusline` ignore a broken pipe on stdout and on stderr (the error EPIPE), so a pipe that Claude Code closes early does not give exit code 1 and a stack trace. Any other error on these streams is not ignored.
- `start` makes sure that `coordinator/.claude/settings.local.json` holds the hook for each event and the status line wrapper. It prints the exact change and the file first, and it asks in a terminal window (the default is no). New flag `start --yes` agrees with no question. It keeps the other keys of the file, and it names a status line that it replaces.
- With no terminal window and no `--yes`, `start` writes nothing and exits with code 2. Inside a factory session, `--yes` gives no consent, so the exit code is also 2, also in a terminal window. Run the command outside the factory session, or answer the question without `--yes`. An answer of no goes on without the hook, and `start` prints one line that names the effect: no last-seen record, so a restart or a reboot can not resume the session by its id. Run `start` again and answer yes to add it.
- A second `start` finds the entries in place, asks nothing, writes nothing, and the file gives no warning. `start --dry-run` shows the change and writes nothing.
- A `.claude` folder or a settings file that is a link, or whose real path is outside `coordinator/`, stops `start` with exit code 4 and nothing is written. A file that is not a JSON object stops it with exit code 1 and stays as it is. The write never touches the settings folder of Claude Code in your user folder.
- Claude Code saves its permission rules in the same settings file, also while a question waits. After your answer, `start` and `init` read the file again. If the file is the same, or the new text gives the same change that you saw, they write the change on the new text and keep what Claude Code saved. If the new text gives another change, they write nothing and exit with code 1. Run the command again then.
- `init` makes the same check for the hook settings as `start`, on a new factory, a received factory and a registered one: `coordinator/.claude/settings.local.json` holds the hook for each event and the status line wrapper. It prints the exact change and the file first, and it asks in a terminal window after its last write and after the question about the setup text (the default is no). `--yes` agrees with no question. A second `init` finds the entries in place and asks nothing.
- Breaking for scripts: with no terminal window and no `--yes`, `init` writes nothing and exits with code 2, before its first write, when the hook settings need a write. A script that ran `init` with no terminal window needs `--yes` now. Inside a factory session, `--yes` gives no consent, so the exit code is also 2, also in a terminal window. Run the command outside the factory session, or answer the question without `--yes`.
- An answer of no goes on without the hook, and `init` prints one line that names the effect and the way to add the hook later: run `init` again and answer yes. A received factory keeps its stop: with no terminal window, `init` stops on a received factory that tracks setup text or other files, also with `--yes`.
- The `safety` block no longer names the folder of the Claude Code files of the user. No file of the program opens that folder, and a test holds its name out of every template.

`upgrade`

- `factory upgrade` migrates a node of version 0.1.0 in one step. It writes `factory.yaml` and `factory.local.yaml` from the values of the old file. A comment of the old file does not stay. It moves the files, renames the managed block, backs up first, and restores the files when a step fails.
- `upgrade` moves `CLAUDE.md` to `coordinator/CLAUDE.md` when the file holds managed blocks. It writes the share list into `.gitignore`. When the folder holds no `.git`, it makes the config repo with one commit of the shared files. It writes no file in `setup/`. After the upgrade of a node of version 0.1.0, `factory doctor` passes.
- An edited block stays as it is, with a warning that names `factory upgrade --overwrite <block>`. An edited `safety` block stops `upgrade` with exit code 4. When `upgrade` replaces a block, it keeps the old text in a backup file in `.factory/backups/`.
- `upgrade` adds the new block `work-rules` to an existing node on layer 1, before the block `setup`. This holds for any block that the factory marker never recorded, when its file is there, except the block `safety`: only the owner adds that block, with `factory upgrade --overwrite safety`, outside a session. A block that the marker records, but that the file lacks, stays missing, and `upgrade` warns and names `factory upgrade --overwrite <block>`, which adds it. `doctor` names `factory upgrade` for a block that `upgrade` adds, and `--overwrite <block>` for any other missing block.
- `upgrade` warns when the role text of a worker is above the cap of 9000 characters. The warning gives the size, the cap and the number of characters that `setup/roles/worker.md` may hold. `upgrade` still writes its files.
- `upgrade` replaces `.factory/roadmaps/README.md` with the new text when the file is still the text that version 0.1.0 wrote. If you edited the file, `upgrade` keeps it and prints a warning. The JSON output lists the file in `replaces`, with the action `replace` or `keep`.
- The `.gitignore` of the state repo ignores `workers/`, the registry of the workers. `init` writes the line for a new factory. `upgrade` adds it to an existing state repo, once, and keeps every other line as it is. A repeat run changes nothing. The JSON output names the action in `stateGitignore`: `create`, `add` or `current`. A `.gitignore` that is a link stops the run with exit code 4, and one that is not a file stops it with exit code 1.
- `upgrade` commits only the files that it writes or moves in `.factory/`. It stops before any change when `.factory/` has a staged change, or a change in a file that the upgrade changes. When a step fails, it clears from the index only the paths that it staged. If git reports an error after the commit was written, `upgrade` keeps the new files and says how to check the commit.
- After a successful upgrade, `upgrade` records the factory folder in the factory list, as `init` does. A problem with the list is a warning.
- The backup holds a regular file with the content of the target when `factory.yaml` or `CLAUDE.md` is a link to a file. If the backup fails, `upgrade` removes the backup folder that it made.
- `factory upgrade --dry-run` makes the new text of each file and checks it, so it reports the errors that the real run reports. The JSON output names the old name of a renamed block in `blocks[].renamedFrom`.
- A node on layer 1 with entries in `children` stops the migration and changes nothing, because the children of layer 1 are workers. A node of version 0.1.0 that lists a project stops it too (exit code 1): make the factory again with `init`. The message gives the remedy.

The delete guard of the state repo

- `init` and `upgrade` write three hooks into `.factory/.git/factory-guard/` and set `core.hooksPath` of `.factory/` to that folder: `pre-commit` (for `git commit`), `pre-merge-commit` (for a `git merge` that makes a merge commit) and `pre-applypatch` (for `git am`). Each hook runs `factory state guard`. A commit stops when it removes an item id from `board.json`, removes the file, or changes it to a text that cannot be read. A commit that does not change `board.json` passes. Git runs no hook for `git revert`, `git cherry-pick`, `git rebase`, `git reset`, and a `git merge` or `git pull` that fast-forwards, so these are not checked.
- The hooks run the Node program and the script by their absolute paths. If a path is gone (a Node update, a second install, a moved package), the hook prints one line that names `factory upgrade`, and the commit stops with exit code 1.
- New command `factory state guard`, for git and not for people. The JSON object of the command is `factory.state-guard/v1`. New field `stateGuard` in the object `factory.upgrade/v1`, with the value `current`, `install` or `unsupported`. `unsupported` means that only a person can repair the guard: `.factory/.git` is a file, a link or another folder; the program path is not known; or the guard folder is a link, is not a folder, is not at its real path, or holds more than 64 entries. `init` and `upgrade` then warn with the cause and a manual step, and go on with exit code 0.
- `init`, `upgrade` and `upgrade --dry-run` print one warning that lists the hooks of the state repo that stop running when the guard is written: the files in `.factory/.git/hooks` that are not `.sample` files, the hooks of another `core.hooksPath`, and the extra entries of the guard folder. Factory runs none of them.
- `upgrade` writes the guard after the ready check, the link checks and the backups, and before the first file change. A stop after that step keeps the guard: "Wrote the delete guard in .factory/.git/factory-guard. It stays."
- `doctor` and `start` warn when the guard is off, and their exit codes stay the same.
- The ready check of `.factory/` stops for a staged change of a submodule pointer. Every git step in `.factory/` runs with the file monitor off (`core.fsmonitor=`, an empty value).
- A key `filter.` or `hook.` in the local git config of `.factory/` stops `init`, `upgrade` and the render of the setup text with exit code 4. For a new `.factory/`, `init` checks the config before its first `git add`, and the remedy names `init.templateDir`.

Git 2.26 and the state lock

- The minimum git version is 2.26. `doctor` fails the check `tools` for an older git, and when it cannot read the git version. `start` reads the git version and the git config of `.factory/` right after its tool check, before it makes or looks at a session. `reboot` outside the session does the same before its first stop. With git older than 2.26, they exit with code 1 before they make or end a session. A dry run of `start` warns. `init` and `upgrade` exit with code 1 for the same fault when they must change `.factory/`.
- One lock file, `.factory/locks/state.lock`, covers each step that changes `.factory/` and commits it. A second writer waits 20 tries of 250 ms, then exits with code 1 and names the lock file. Three steps only warn, write nothing and go on with exit code 0: the claim of the active machine by `start`, the clear of the mark by `shutdown`, and the clear of the mark in the end step of `reboot`.
- The lock file holds an owner token, `<pid>-<16 hex characters>`. A step that ends removes the lock file only when it holds its own token. A lock file older than 300 seconds is taken over, and the new lock file holds the token of the new owner.

The heavy-test lock

- New command `factory lock run [--priority] -- COMMAND`. It runs one heavy command after the other heavy runs of the user have ended, and it waits up to 90 minutes. The exit code of the command passes through, and each outcome that factory decides writes one stderr line that starts with `error: factory lock run:`. The text of the block `worker` names this command, so `upgrade` renders it again. See the README, "Run a heavy command".

`doctor`

- `factory doctor` runs 31 checks. Version 0.1.0 ran 11. The new checks are `local-file`, `root`, `temp-folder`, `index`, `node-id`, `setup-text`, `roles`, `tracker`, `children`, `root-repo`, `root-files`, `project-paths`, `delegations`, `instruction-files`, `project-urls`, `agent-version`, `state-guard`, `board-size`, `lessons` and `role-delivery`.
- `role-delivery` checks the path from the setup text to the worker sessions. Its line counts the work copies whose hook settings hold the hook of factory for every hook event, gives the size of the role text against the cap of 9000 characters, and names the place of the acceptance of the setup text. No worker is ok. A fault of the role text fails the check. A work copy that lacks the hook for one or more events, or whose hook settings file is a link, is a warning. The finding names the missing events, and the check uses the same rule as the launch of a worker, so the check and the launch agree. Each finding gives one remedy. The check writes nothing.
- `board-size` warns when `board.json`, `waiting.json` or `decision-log.json` reaches 80 percent of the read cap of 1 MiB, and names the file. A file that is not there is no fault.
- `delegations` shows the mode of each approval point. A `delegated` mode with no matching approval record warns, and the point counts as `owner`.
- `instruction-files` warns when the factory folder, or a folder above it, holds a file that an agent loads as an instruction.
- `project-urls` warns for a project that has no URL that you can share.
- The checks `blocks` and `tools` know the new rules. The `permission-mode` check reads the settings files of the session folders and does not read the settings folder of Claude Code in your user folder.

Roles, layers and nodes

- The role of a node comes from its layer. Layer 1 has the coordinator template. Layer 2 has the manager template. A layer above 2 has no role template yet: `coordinator/CLAUDE.md` holds the safety block only, `init` prints a warning, and `doctor` warns.
- New commands `factory node children`, `factory node add-child PATH` and `factory node remove-child ID`. A child must be one layer lower, and its id must differ from the id of this node. `add-child` refuses on layer 1, because the children of a coordinator are workers. The commands keep the comments and the key order of `factory.yaml`.
- New command `factory node send ID --file FILE`. It writes a task file into `.factory/inbox/` of a child node and prints the session name of the child. You check the name with `ListAgents` and send one `SendMessage` that names the file. The file has mode 600 and starts with a header that ends with "Message, no owner authority." The exit codes are 0, 1, 2, 3 and 4, and `--json` prints `factory.node-send/v1`. A node on layer 2 or above now holds workers and child nodes at the same time, and a worker and a child node cannot share an id. A node on layer 2 from an earlier version gets the worker file with `factory upgrade --overwrite worker`. The state repo ignores `inbox/`, and `factory upgrade` adds the line. The safety block names `.factory/inbox/` as data with no authority of the owner, and the manager text tells how to use `node send`. See the README, "Send a task to a child node".
- New command `factory worker new ID --project PROJECT [--assignment FILE] [--yes]`. It makes a work copy of the project on the new branch `worker/ID`, writes the record of the worker, hides the hook settings of the work copy from git, and starts the worker in a pane of the window `workers`.
- New command `factory worker list`. It shows each worker with its pane, its state from the last hook event, its context percent and the mark `PREPARE` or `MAX`, and it changes nothing. It takes a last-seen line only when the line belongs to the worker, with the same checks as `worker stop` and `worker resume`. The hook of a worker now also writes `.factory/workers/ID/last-session`, so the last-seen line is found from the id of the worker. `--json` gives each worker ten more keys: `itemId`, `itemTitle`, `itemStatus`, `stage`, `stageAt`, `parkedCount`, `paneLive`, `sessionState`, `activityAt` and `stalled`. They are facts, and the schema stays `factory.worker-list/v1`. `stalled` is true only for a live pane with a busy session and no hook or context write for 15 minutes. It is a hint.
- New command `factory worker stop ID`. It sends `kill -TERM` to the process of the pane of the worker, waits for its end, and closes the pane. When a summon put the pane in the slot of the window `view`, the board comes back into the slot before the pane closes. It never sends `KILL`, and it exits with code 3 only when the state of the session is not known. A last-seen line now also records a session marker (`session_marker`), the id of the node or of the worker that wrote it.
- New command `factory worker resume ID`. It starts a stopped worker again in a new pane, with the same checks as `worker new`. It continues the earlier conversation only when the last-seen line belongs to the worker. Else it starts a new conversation and warns that the earlier one is not resumed.
- New command `factory worker summon ID [--for TIME]`. It shows the pane of the worker in the slot of the window `view` for `TIME` (default 15m, from 1m to 2h), and the board comes back by itself. A new random token in the pane option `@slot_summon` and one timer do this, and a newer summon replaces the token, so an older timer does nothing. Exit code 3 names `factory start` when no tmux session runs, and `factory worker resume` when the worker has no live pane.
- New command `factory layout`. It makes the window `workers` if it is missing, tiles its panes, and puts the board back in the slot of the window `view` after a summon. It works on a session that has only the window `view`.
- New command `factory shutdown`. It stops each worker with `kill -TERM`, also a busy one, clears the mark of the active machine, stops the coordinator with `kill -TERM`, and then ends the tmux session by its exact name. `factory reboot` from outside the session stops the coordinator the same way. It stops only what factory started for this factory folder. A session of the same name that belongs to another folder, or that has no home option, stays, and the command exits with code 4. With no session it says that nothing runs and exits with code 0, and it still clears the mark of the active machine of this machine. A worker in a state that is not known makes it exit with code 3 and stop nothing.
- New command `factory restart ID`. It stops one worker and starts it again with its session id. The other workers keep their panes. A worker with no usable session id, or in a state that is not known, makes it exit with code 3 and stop nothing. With no session it exits with code 3 and names `factory start`. A failing root check or settings check exits with code 4 before any stop. A proxy of the worker that does not answer exits with code 1 before any stop.
- New command `factory reboot`. It stops every worker and starts each recorded worker again with its session id. Outside the session it first makes the steps of `start` that change a file (the safety block rendered again when it is out of date, and the hook settings of the coordinator), then it ends the session and starts it again with the recovery of `start`. In a pane of the session it keeps the session and the coordinator pane. One run asks each proxy once, before the first stop: a proxy that does not answer makes it exit with code 1 and stop nothing. A worker that fails a check makes it exit with code 3 and stop nothing.
- New command `factory status`. It shows each worker with its state (`stopped`, `at prompt`, `busy`, `waits` or `unknown`), its work item and its idle state, with one `list-panes` call. It writes only the report file (see `factory report`). A worker is idle when its last activity is older than `limits.idle_after` and it has no open work. A work item that is not known never makes a worker idle. The work item comes from the local board. A factory with no `board` block, or with a block that names no worker field, shows `unknown` for every worker. `--json` prints the object `factory.status/v1`. The text, the object and the exit code do not depend on the report file. A link at the report file stops `status` with exit code 4. Any other fault of the write is one warning, and a board that cannot be read gives that warning too. Each worker of `--json` has the same ten keys as `worker list --json`, and its `workItem` holds the evidence of the board only.
- New command `factory report [--home DIR] [--json] [--since CURSOR]`. It shows the report of the node: a verdict line (`OK:` or `CHECK:`) with the counts of workers, items in progress, requests and children, then one row for each child node. `--json` prints the object `factory.report/v1`. The exit code is 0 for a report that is built, also with the verdict `CHECK:`. It is 1 when the board cannot be read, when the report is over a cap, or when the file cannot be written. It is 2 for `--since`, and 4 for a security stop. The report has no events yet and its cursor is null, so `--since` exits with code 2 for now. The work item of a worker in the report is `{"state": "known", "item": ID or null}` or `{"state": "unknown"}`, so null means only that the worker has no open work. The board counts of the report give all items by state and the open items by each owner field. A list of counts keeps at most 256 rows, the highest count first, and gives the number of the other names in `statesOmitted` and `valuesOmitted`, so a long list never stops the report. `report` and `status` build the report with one builder. Both write it to `.factory/outbox/report.json`, with the same text that `report --json` prints, in a file of mode 600 in a folder of mode 700. The write replaces the file whole. The file is fresh only after `report` or `status` runs. The state repo ignores `outbox/`, and `factory upgrade` adds the line. See the README, "Show the report".
- New command `factory node tree [--home DIR]`. It shows one line for each child node of the config and for each node below it, from the report files of the nodes. It reads files only: it scans no folder, pings no node and starts no process. Before it reads a report file, it checks the metadata of the `factory.yaml` in the same folder, as `node children` and `report` do: no link, the same account, no write bit for a group or other users. It reads no text of that file. A node that fails gives `unknown` with the same fixed reason as in `node children` and `report`. The first line is the verdict line (`OK:` or `CHECK:`). A line below a direct child has the mark `reported by ID`. A cycle, a duplicate id, a cap or a dropped request gives a `warning` line. The walk goes at most 16 layers down, reads at most 1,000 report files and 16 MiB in all, and prints at most 2,000 rows, plus the verdict line and the cut line. The exit code is 0, also with `unknown`, `mismatch` and `warning` lines. `--json` prints `factory.node-tree/v1`, and all text from a child is in the field `report`. See the README, "Show the tree of child nodes". The child rows of `report` now hold the counts and the age of the report file of the child. A parent reads that file with fixed checks: no link, the same account, no write bit for a group or other users, a byte cap and the report schema. It opens the file one time and checks that open file. The open does not follow a link and does not wait. A file that fails gives `unknown` with a fixed reason. A child that answers but has no report file is `unknown` until it runs `factory report`. A child with another id than the config lists now shows `mismatch`, not `unknown`, in `node children` (also in `--json`, `factory.node-children/v1`), in `report` and in `node tree`. `doctor` now fails the check `children` for it. Before, it gave a warning. `node add-child` refuses a child `factory.yaml` that is a link, belongs to another account, or can be written by a group or by other users, and `node children` shows such a child as `unknown`. A child `factory.yaml` that is not valid gives a fixed reason with no key names. Run `factory doctor` in the child folder to see the detail. Each value in the child list is now one clean line with a width cap.
- A command with no `--home`, no `FACTORY_HOME` and no `factory.yaml` above finds the factory from a git work tree of a listed project, also when the work tree is outside the factory folder (for example a work tree that `git worktree add` made). `status` uses this. A work tree of no listed project exits with code 2 and prints the hint.
- New command `factory dismiss ID [--yes]`. It ends the pane of a worker, removes its work copy with the plain `git worktree remove` (never with force), and deletes its record and its last-seen line. It is a dry run until `--yes`. The checks come before any change. The work copy must be a folder below `work-copies/` with no link in its path (exit code 4). Its file `.git` must name the git folder that the clone keeps for it, else `dismiss` stops with exit code 4 and runs no git command in the work copy. A worker that is busy or waits in a dialog, that has open work, or whose state is not known is refused (exit code 1). The work must be pushed: after one fetch for each clone, the head must be on the remote copy of `worker/ID` or on the default branch of the remote, and the work copy must have no changed file, no untracked file and no stash entry. If not, `dismiss` prints one `STUCK:` line for each reason, frees nothing and exits with code 1. The removal also deletes the files that git ignores in the work copy, so the dry run and each free name them: their count and at most 20 paths. The branch stays, and the output prints the `git branch -D` line that deletes it. `--yes` gives no consent inside a factory session (exit code 4).
- New flag `factory dismiss --idle`. It lists the idle workers with their state and whether their work is pushed, and changes nothing. In a terminal window outside a factory session you type the ids to dismiss, and only the panes of the picked workers end. Each free names the ignored files that it deletes. After you type the ids, `dismiss` reads the state of the workers a second time and checks each picked worker again before the first change. With no terminal window it only lists. Inside a factory session the pick step exits with code 4. With no `board` block, or with no worker field in it, no worker is idle.
- The remedy of `worker new` for a work copy that it kept names `factory dismiss ID`.

The local board

- New commands `factory item add|update|move|close|list`, `factory track add|list`, `factory request add|list|close` and `factory queue set|show`. They read and write `board.json`, `waiting.json` and `decision-log.json` in `.factory/`. Each write takes the state lock once and makes one commit in the state repo. A read takes no lock. A board kind other than `local` refuses a write with exit code 4 and makes no commit. No command needs python3, jq or glow. See the README, "Use the local board".
- New optional block `board` in `factory.yaml`. It names the item states, the item fields and the queue-row fields, with their allowed values, and the field that holds the worker. The block is strict, and the local file refuses it. The schema version stays 2. With no block, `item add`, `item close` and `item move --state` exit with code 2 and point to the sample `examples/factory.board.yaml`.
- A track is a named stream of work. `board.json` has the new optional key `tracks`. A stage is where an item is on the board. The recipe gives the list of stages. The stages `merged` and `released` are only set by a flow, so `item move` refuses them with exit code 2. A stage is display data and never an approval. An item holds `stage_at`, the time of its last stage change, as an exact UTC time. Only a change of the stage writes it.
- `item list` prints one line for each track, with the counts by stage. `--track ID` lists the items of one track, and `--all` shows the closed items too. The output has at most 20 lines. `--follow` draws the list again at each change of the board file, and it ends on SIGHUP, SIGTERM, a failed write, a change of the parent process, or a stdout that is not a terminal window.
- `request add` gives the next number `D-n` above the highest number in the waiting file and the decision log. `request close` writes a log row "closed with no answer" with no `by`, and a log row with no `by` is no owner decision. `queue set` finds a row by its exact name, makes a new row when no row has the name, and `--item` replaces the whole list of items. The queue has at most 30 rows, and a row has at most 30 items. `request add` also stores `opened_at`, the UTC time of the add, and `group`, which is `now` or, with the new flag `--later`, `later`. So a new waiting row holds two more keys. `request list --json` gives `openedAt` and `group` for every open request, and `openedAt` is null for a row from before this version. `decide` shows both values and refuses a stored value in a wrong form.
- `request close ID --made-by coordinator|delegate --decision TEXT` closes a request that the coordinator or a delegate decided. Use it only for a request that is not an approval point. The log row holds the decision and the key `decider`, and it has no `by`, so it has no owner authority. `factory.request/v1` gets the field `decider`, null for a close with no answer. The coordinator and worker texts say that each relay of a decision names who made it.
- A text over 1 MiB for one of the three board files is refused (exit code 1), and nothing is written. A board file that is corrupt, is not valid UTF-8 or holds a repeated id stops the command (exit code 1) and names the file. A command that prints a stored text removes control, bidi and invisible characters, turns a line break or a tab into one space, and cuts the line to 120 characters. In `--json` output, only control, bidi and invisible characters are removed from string values. A line break stays as an escape, and no string is cut to a width.
- The right pane of the window `view` (the slot) runs `factory item list --follow`, so it shows the board.
- `status` and `dismiss --idle` take the work item from the local board.
- The coordinator text has a new Board section that names the board commands. It says that a stage is never an approval. The text of the block `coordinator` changes, so `upgrade` renders it again.
- The package now holds the folder `examples/` (the new entry `examples` in the `files` of `package.json`). It has the sample `factory.board.yaml`: a `factory.yaml` with a `board` block. A test loads it through the config schema.
- `upgrade` renames the queue key of `board.json` from `queue` to the queue key of the recipe, in the commit of the upgrade. The dry run prints the line `.factory/board.json: rename the queue key "queue" to "<key>". Your other text stays.` `--json` of `upgrade` has the new field `boardQueueKey`, with the value `rename` or `current`. If the new text would lose an item id, `upgrade` stops with exit code 4.
- New command `factory item record ID --ref REF [--project PROJECT]`. It runs the record check of the recipe of the node, and it writes only after the check passes. With the software recipe, REF is the number of a PR. The check reads the PR with `gh` and passes only for a PR of a GitHub project that is merged into the default branch. The default branch is the key `default_branch` of the project, else the branch that `origin/HEAD` of the clone names. If neither is set, the command exits with code 1. If the item names a worker, the PR must come from the branch of that worker. If the item has no worker but names former workers in `unassigned_from`, the PR must come from the branch of one of them. A PR whose head commit another item records already is refused. Every fault of `gh`, and every PR that does not match, is exit code 1 with no write. A bad PR number is exit code 2 before any call of `gh`. One commit sets the stage `merged`, closes the item, keeps the head commit of the PR in the item key `merged_pr_head`, and takes the item out of each queue row that lists it. A row that becomes empty goes. The command never merges a PR. A second run for the same PR succeeds and makes no commit. A recipe with no record check makes the command exit with code 2 and write nothing. `item move --stage merged` is still refused.
- New command `factory item unassign ID`. It runs only in the coordinator pane. It deletes the worker field of the item, keeps the stage and the state, and adds the id of the former worker to the item key `unassigned_from`.
- `item update` now refuses a change of the worker field of an item whose worker field holds a value. The exit code is 2, the board does not change, and the message names `item unassign`. A patch with the same value is no change. `item update` can still set a worker on an item that has none, and `item add` can still set a worker.
- The field names `merged_pr_head`, `unassigned_from` and `stage_at` are reserved. A `board` block with an owner field of one of these names fails the config check, and the error names the remedy: rename the field. An owner field named `stage_at` is refused from this version. If items hold values in a former owner field `stage_at`, move the stored values to the new field name before the next stage change. A stage change writes `stage_at` and replaces the old values with no message.
- From a `v0.2.0-ea.N` build before this change: an item has no `stage_at`, and an open request has no `opened_at` and no `group`. There is no migration. A view reads null for the times and `now` for the group, and the next stage change of the item writes `stage_at`. A `decide` of an older build refuses a request row that this version wrote, so use one build on one machine.
- New flag `factory request close ID --relayed --decision TEXT`. It runs only in the coordinator pane. It closes a request with an answer of the owner that the coordinator passes on. The log row names the coordinator as the decider, has the key `relayed` with the text "owner answer, relayed by the coordinator, no owner proof", and has no `by` key. The command writes no owner store record, so a relayed answer is never proof of an answer of the owner. `--relayed` takes no `--made-by`. `decide` on a request that was closed this way refuses and names the relay.
- New command `factory request log --made-by coordinator|delegate --title TEXT --decision TEXT`. It writes one log row with the next number `D-n` in one commit, and it makes no request in the waiting file. The owner is not a value of `--made-by`.
- When `upgrade` changes the block `coordinator`, it prints one line: the next `start` resumes the earlier coordinator conversation, and that conversation must follow the new rules. `start` and `reboot` print a like line when the coordinator resumes. The pointer to the conversation does not change.
- The text of the block `coordinator` has the rules for the commands above, and a section that tells a resumed coordinator to follow the new rules and to drop a workaround that a new rule replaces. An existing factory needs `factory upgrade` for this text. These changes close the gaps that the second trial of workers showed.

The worker life cycle

- `worker watch` runs up to 24 hours: at most 2,880 checks, one every 30 seconds. Before, it ran at most 40 checks.
- `worker watch` reports a finish of a worker. A finish is a last-seen line with the event `Stop` that is newer than the baseline of the worker. The event `SessionStart` is no finish, and a worker of `--ready` has no finish. The JSON kind is `finished`.
- New flag `worker watch --since TIME`. TIME is a UTC time that ends with Z, the form that the output prints. A finish that came after TIME is a report, also when it came before the first check. Any other text is exit code 2. The flag is exit code 2 on the other `worker` commands.
- Each line of the output of `worker watch` ends with `last check TIME`, and the JSON has the field `checkedAt`. The line `NO WORKER:` has no time.
- One watch runs for each node. A new run in the coordinator pane writes a token to the run marker `.factory/state/worker-watch-run`, and the older run ends at its next check with `REPLACED: a newer watch runs` (exit code 0). A run marker that is lost is exit code 1 with `watch marker lost`. A `--ready` run also replaces the general run. A run in a shell outside the factory sessions takes no run marker and does not read it, so it does not replace the run of the coordinator. A run that finds no worker with a pane takes no run marker. A run ends with `ENDED: the parent process of the watch changed` when its parent process changes. The watch writes only its run marker.
- Inside a factory session, only the coordinator pane runs `worker watch`. Any other pane is exit code 2. A shell outside the factory sessions still may run it.
- Known limit: the last-seen file keeps only the latest event of a worker, so a finish that a new turn follows between two checks is not seen.
- The meaning of `idle` changes. The column `IDLE` of `status` and the JSON field `idle` are `yes` only for a worker with a live pane at the prompt whose last event is older than `limits.idle_after`. The time of the context percent does not count, and the work item does not count. Before, the field also needed no open work. The hint of `limits.idle_after` in the config file says the same.
- `dismiss --idle` lists only idle workers whose work item the board knows and that have no open item. Its table has the new column `IGNORED`: the count of the ignored files that the free deletes, `more than 20`, or `-` for a worker whose work is not pushed. The table goes to the screen before the question. The JSON entries have the keys `ignoredCount` and `ignoredMore`.
- The dry run of `dismiss ID` names the files of the inbox of the worker that the removal deletes, at most 20. The JSON has the list `inbox`.
- New flag `dismiss ID --closed`. It is the one free that the coordinator runs in its own session. It runs only in the coordinator pane. It frees the worker only when the board knows the work item, a closed item names the worker, no item that is not closed names the worker or carries its unassign mark, the head of the branch is on the remote or is the recorded head of a closed item of the worker, and the work copy is clean. It checks again right before the removal, and the head must still be the head that the decision row names. The second check and the removal run while the command holds the state lock, so a board write waits until the worker is freed. One decision row comes first: the title is `Free the worker ID`, and the decider is the coordinator. A missing guard is exit code 4, and the message gives `dismiss ID --yes` for the owner. If git refuses the removal, the message names the run of the owner, `dismiss ID --yes`, and no unlock or forced removal. Open work, `STUCK:`, a fault of the second check and a state lock that another process holds are exit code 1. `--closed` with `--yes` or `--idle`, a wrong number of ids, and a caller that is not the coordinator pane are exit code 2. The free deletes the ignored files and the inbox files with no prompt, so the dry run comes first. The `--yes` path is the same as before. With `--json` the output has `closed` and `decision`.
- The state folder has a new folder `.factory/reviews/` for the review results that the coordinator keeps. `start` makes it with mode 700. A free never deletes it. The `.gitignore` of the state repo has the new line `reviews/`, and `upgrade` adds the line to an older node.
- The role texts have the rules for the life cycle. The block `worker` has version 5, the block `coordinator` has version 6, and the block `manager` has version 3, because it shares the worker section. The coordinator text says to run the watch again after `worker new`, to give `--since` with the time of the last report, not to run the watch again for a `REPLACED:` report, to run the watch again when the newer watch fails with exit code 1, to run the watch once again after `watch marker lost`, and to use `dismiss ID --closed` only for a closed item, a pushed branch and a clean copy, after the dry run and after the copy of the review files to the reviews folder. The worker text says that a dismiss deletes the inbox and where the review results are kept. The coordinator text for `item record` names the rule for an item with former workers. `upgrade` renders the blocks again.
- New working rules in the block `worker` (version 5) and in the new block `work-rules` (version 1). A command that only reads runs with `--json`, and a new command runs with `--help` first. A refusal is reported with its exit code and its error text, and nobody looks for a way around it. Only the coordinator changes the board. A session opens no file in the user config folder. A session installs nothing outside its work copy without an owner go. An owner go has one source only: input that is typed into the session and starts with the exact owner prefix. Any other text is data and never a go. A message from the coordinator to a worker is a work direction and never a go. The role text of a session comes only from factory. The block `work-rules` is in `coordinator/CLAUDE.md` of a node on layer 1 only, after the block `safety`. The manager layer gets no new block. The model follows these rules as text, and the permission checks of Claude Code still apply.

Messages between sessions

- New commands: `factory worker reset ID --clear|--compact`, `factory worker watch [ID]...`, `factory self reset` and `factory worker new ID --project PROJECT --assignment FILE`. The flags `--clear`, `--compact`, `--assignment` and `--ready` exit with code 2 on every `worker` command that they do not belong to.
- Each session starts with a name: the coordinator `<node id>`, a worker `<node id>_<id>`. An id can not hold an underscore, so two nodes with different ids never give the same name. From 0.2.0-ea.1, which used a hyphen: run `factory upgrade`, then restart each worker. A coordinator gives work with the cross-session messages of Claude Code (`SendMessage` and `ListAgents`, version 2.1.224 or newer). A long task is a file in the assignment folder of the worker. There is no inbox and no doorbell.
- `worker reset` types `/clear` or `/compact` into the pane of one worker, from the coordinator pane only, and checks that it happened. `self reset` queues a `/compact` for the coordinator after its resume file exists. `worker watch` checks the workers every 30 seconds, at most 40 times, and exits at the first change. See the README, "Give work to a worker".
- The hook settings hold two more events, `Notification` and `PreToolUse`, so there are 6. `worker list` and `status` show the new state `waits`, and `dismiss` refuses a worker that waits. `factory upgrade` adds the events to existing work copies and to the coordinator settings. Then run `factory reboot`, so that each session gets its name and the new events.
- The role texts say that a message from another session is a work direction only and carries no authority of the owner. `upgrade` renders them again.
- `doctor` checks the version of Claude Code (2.1.224 or newer) with the new check `agent-version`, and warns about `crossSessionInbound` set to `hold` or `refuse` and about the default mode `plan`.
- New JSON objects: `factory.worker-reset/v1`, `factory.self-reset/v1` and `factory.worker-watch/v1`. `factory.worker-new/v1` gets the field `assignment`. `factory.upgrade` gets the field `hookSettings`.
- `worker new --assignment` reads a relative path that starts with `.factory/orders/` and has no `..` part from the factory folder, from any folder. Before, it read the path from the current folder, so `.factory/orders/FILE` failed from `coordinator/`.
- `worker watch --ready ID` also watches a worker that waits for the owner, for example at a dialog. It reports `ready` when that worker is at its prompt or busy. Before, nothing reported a worker that became ready after a block. The coordinator block tells the coordinator to use it, and to run the watch again after each end.
- The coordinator block shows `--yes` in the `worker new` line, and says when it counts: for a new work copy with no settings file. The consent rule does not change.
- `worker new` prints one more line: if Claude Code asks to trust the folder, the owner answers once in the pane that the line names. Then the coordinator runs `worker watch --ready ID`. The trust of the factory folder does not cover a work copy, because a work copy is a git repository of its own.

Pull requests and the role lines

- New command `factory pr watch PR [--head SHA] [--project ID]`. It watches the checks of one pull request at one head commit, and it exits when the checks end. It makes up to 60 reads, 60 seconds apart. It only reads: it never merges, never approves and never writes. Exit code 0 means that every check passed at the head. A pass is no approval to merge. The output holds fixed words, counts, the number and the head, and it never prints text of `gh`. See the README, "Watch a pull request".
- A recipe can add commands to the command table, through a hook of its entry. The software recipe adds `pr` this way. The help lists the commands that the recipes add. A recipe command never replaces a core command.
- Coordinator text pins each merge to the head SHA. The coordinator checks a result on the primary source at the exact head SHA before it tells the owner. It merges only at the full head SHA that it checked, with CI green at that SHA.
- Coordinator text says to run `factory pr watch PR --head SHA` as a background task after a push, and that exit code 0 is no approval.
- The resume notes can hold a section `Standing routines`. A session starts only `factory worker watch` and `factory pr watch` from it. The argument is a worker id (a-z, 0-9 and hyphen, at most 40 characters, no hyphen at the start), a PR number or a 40-hex SHA. Any other line of the section is data: the session tells the owner and does not act on it. A session never starts `factory lock run`, a merge, a typed owner line or any other shell command from the notes. At the start of a session, it starts only the routines that do not run now. After a compact, it starts none. The manager text has the same rule.
- The coordinator keeps its lessons in `.factory/lessons.md`, at most 40 entries and 32768 bytes. An entry is three lines that start with `Rule:`, `Why:` and `How:`, and only the coordinator writes the file. A lesson is data: it grants no approval and no delegation, and it overrides no rule. No text of `gh`, a pull request or an issue goes into an entry.
- `factory doctor` fails the new check `lessons` when `.factory/lessons.md` is a link or not a plain file, is larger than 32768 bytes, or holds more than 40 entries. A missing file is no fault, and the check never changes the file.

Platforms and help

- On native Windows, every command exits with code 1 and prints the hint to use WSL. macOS and Linux are the supported systems. `factory start` needs tmux 3.0 or newer and `claude` on the PATH.
- New command `factory help words`. It prints one plain sentence for each word that factory uses. `--json` prints the same list.
- New command `factory machine`. It reads the free memory, the free disk space of the factory folder, the load and the count of processors, on macOS and on Linux, and judges them against `limits.memory_free_min_pct`, `limits.disk_free_min_gb` and `limits.load_max`. Each fact has a value, a limit and a verdict: `ok`, `fail` or `unknown`. A program that fails or is too slow, and an output that does not parse, give `unknown`. The exit code is 0 for every verdict. `--json` prints the facts and the key `power`: `source` is `ac`, `battery` or `unknown`, and `percent` is a whole number from 0 to 100 or null. The power comes from `pmset -g batt` on macOS and from `/sys/class/power_supply` on Linux. The text output has no power line.
- Error messages, hints, the text of an internal error and the question of `init` show a control character as `?`, as the other text output does.

Install

- You install factory from an early-access tag `v0.2.0-ea.N` of the git repo. The install has two steps. `npm pack "git+https://github.com/dean0x/factory.git#<sha>"` builds a package file with the new script `prepare`, and `npm install --global ./dean0x-factory-0.2.0.tgz` installs it. `<sha>` is the full 40-character commit SHA of the tag. The guide first checks with `git ls-remote` that the tag points to `<sha>`, so the build is the commit that was checked and not the tag name. npm can not build the program in a one-step global install from git.
- `package.json` now has `"private": true` and keeps `publishConfig`. FAC-M10 removes `private` after the owner writes the decision id.
- The package now holds the guide `docs/quick-start.md`. It lists the prerequisites with their checks, the install, the update, the tmux keys and the known limits.
- A `v0.2.0-ea.N` tag is no release. There is no GitHub Release and no npm publish. `factory version` prints `0.2.0` for every build, so the tag and the commit SHA name the build.
- CI proves the install from git on Linux and on macOS with `npm run install-check`.
- The README has a section for outside users: the status of the project, what the ids in `docs/` mean, and how to report a problem. The guide `docs/quick-start.md` now installs from the public repo, with no login.

Security

- `start` and `doctor` find a Claude settings file that skips the permission prompts, that sets or clears an `env` variable whose name starts with `FACTORY_`, or that sets the proxy or the credential of the session in `env`, in `coordinator/`, in a project folder or at a tracked path. `doctor` fails and `start` exits with code 4. A settings file in `coordinator/` or in a project folder that runs a command (a hook, a status line or a key helper) stops them too. The hook and the status line that `factory` writes itself do not count.
- The stop for a status line that `factory` did not write now tells the owner to check the command first, then names the way to keep it: set `session.statusline` in `factory.local.yaml` to it, and `factory` runs it and shows its output. A stop for a hook or a key helper only does not get this sentence.
- A check of a security boundary that can not finish stops `start` with exit code 4, and `doctor` fails: git fails, a settings folder holds more than 64 settings files, or a settings file can not be read.
- The token scan names a tracked file that holds a NUL byte (a binary file or a file in UTF-16) as not scanned. A base64 secret that holds a slash and no plus sign is no longer taken for a path.
- `start` and `doctor` warn about a rule that allows a whole tool and about a setting that approves project MCP servers.
- `init` and `start` exit with code 4 when the config repo tracks `factory.local.yaml`, a path in `.factory/` or a path in `coordinator/`, or when git does not ignore the local file or the state folder. `doctor` reports it.
- `doctor` fails, and `start` exits with code 4, when a tracked text file holds a value that looks like a password or a token. The message names the file and never prints the value.
- A clone URL with a password, a token or a user name in an `https://` URL is refused (exit code 2) before any clone. `init` never writes such a value.
- A project path that is outside the factory folder, or reserved, is refused (exit code 4) before any clone.
- A received factory needs your acceptance of the setup text and of every other tracked file before `start` runs. A tracked link stops the command with exit code 4. A list of tracked files over its cap stops `start` with exit code 4 on every factory, and `init` too on a received factory.
- Only `init` in a terminal window outside a factory session writes the record of a `delegated` approval point.
- `init`, `upgrade` and `start` exit with code 4 for a link, or for a path that resolves outside the factory folder, in `setup/`, in `coordinator/` or in the backup of a block.
- The factory list and the stores of the approval records and of the setup acceptances are files of mode 600 in a folder of mode 700. `factory` refuses a file that another user owns or that a group or other user can write.
- `upgrade --overwrite safety` is for the owner. It exits with code 4 inside a factory session.
